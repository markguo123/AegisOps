# P12.1 多集群链路核验与缺口记录

- 日期：2026-11-13
- 依据：方案 22 v1.1、四期开发计划 §12、AGENTS.md
- 范围：只核验当前代码与本地可复现测试，**不连接任何真实 A/B/C 集群**。
- 结论：已有目标绑定主链路可复用；复杂 shell、凭据原位更新、检查时间/原因、工作台与入口存在缺口，已按 P12.2–P12.5 补齐自动化部分。P12.6 真机联验未完成。

## 1. 核验方法

逐入口阅读并交叉核对以下链路，不根据旧设计推断：

1. Web/API 入口：`internal/server`、`internal/sessionapi`。
2. 会话/运行绑定：`internal/service/chat.go`、`internal/service/platform_run.go`、`internal/authz`。
3. 集群与凭据：`internal/cluster`、`internal/store`。
4. 工具装配：`internal/tools`、`internal/tools/k8s`、`internal/tools/diagnosis.go`。
5. 执行与写后验证：`internal/executor`。
6. 体检与报告归属：`internal/server/scans.go`、`internal/server/reports.go`、`internal/service/reports.go`、`internal/store/reports.go`。
7. 前端：`web/src/views/chat`、`web/src/views/cluster`、`web/src/views/report`、`web/src/components/chat`、`web/src/composables/useClusterAccess.ts`。

本地借鉴项目核对：

- `借鉴项目/holmesgpt/docs/data-sources/builtin-toolsets/kubernetes-mcp.md`：同一 Holmes 实例通过统一工具集合访问多个 context；它由模型在每次调用中选择 context，并明确用 MCP 工具替换重叠的内置 kubernetes 工具。
- `借鉴项目/holmesgpt/docs/installation/k9s-installation.md`：每次调用生成临时 kubeconfig、切到明确 context，避免修改用户全局 current-context。
- `借鉴项目/kagent`：Agent 定义与可复用 ToolServer 分离；CLI 的 `kubectl`/kubeconfig 工具走进程默认 kubeconfig，不构成本项目的多集群授权模型。

**借鉴边界**：采纳“统一能力装配 + 每次运行独立临时 kubeconfig + 不修改全局 context”；**不采纳**由模型传 `context` 决定平台执行目标，也不引入 kagent 的 CRD/Controller、HolmesGPT 的 shell 脚本、`--raw` 命令或 MCP 工具替换机制。AegisOps 的目标必须由服务端会话/任务绑定，模型不可见、不可改。

## 3. 关键链路细节

### 3.1 会话与运行

- 会话固定目标：`Session.Cluster` 是稳定 ClusterID；coverage 是创建时授权快照。
- 发消息时服务端重新读取 coverage 与 `EffectiveAccess`，不信任前端选择或模型参数。
- `PlatformAccess.Bind`：
  1. 当前请求重新核验登录主体；
  2. 按 ClusterID 取有效授权并检查覆盖；
  3. `ExecutionConfig` 解密、`api.MinifyConfig`、校验便携凭据；
  4. 写入权限 0600 的临时 kubeconfig，进程结束 `Close` 删除；
  5. `Access` 每次重验授权与凭据版本（版本是密文 SHA-256）。
- 撤权/轮换：15s `Watch` 取消运行；P12.2 又增加每次 kubectl 执行前 `TargetCheck`，不再只等看护周期。

### 3.2 工具与子进程

- 结构化读、诊断、Secret、client-go 写都从同一个绑定 kubeconfig/RESTConfig 构造。
- kubectl 与 client-go 写共用同一临时 kubeconfig；没有全局 current-context 变更。
- 写后验证使用同一 clientset，不另建“默认集群”客户端。
- 审计与报告使用 `Session.Cluster` / `ScanOptions.Attribution.ClusterID`，不是资源名推断。

### 3.3 复杂 shell 的实际风险

核验发现旧路径的安全结论不成立：

1. `kubectl.go` 的 shell 分支 `cmd.Env = os.Environ()`，再追加 `KUBECONFIG=...`；进程环境里若已有 `KUBECONFIG`，子进程可能继承多个值，行为依赖解释器取值顺序。
2. bash 内可写 `KUBECONFIG=/other kubectl ...`、使用 `--context/--kubeconfig/--server`、读取 `~/.kube/config` 或调用任意程序；人工审批只能证明“用户同意执行这段文本”，不能证明“实际 API 目标仍是绑定的集群”。
3. 受控只读组合本身安全，但它是 cmdplan 证明后的 argv 路径，与任意 shell 是两条不同通道。

结论：在多集群平台模式（服务端绑定临时 kubeconfig）下，**无法证明目标的 shell 路径必须拒绝**；保留受控只读组合与现有真人审批。该决策与方案 22 §8.1 一致，不扩大 shell/Secret 权限。

## 5. A/B/C 能力一致性清单

同一平台配置下，A/B/C 共用同一套：

- Agent Runtime、模型、工具注册、Skill、诊断子调用、审批策略、Executor。
- 结构化读、日志、事件、诊断、kubectl 只读组合、写入、写后验证、Secret 专用通道。
- 体检预设、扫描器、报告归档与报告读侧授权。

每次运行只允许一个目标；目标不匹配时确定性拒绝，不回落 A、不切换到“最近成功”的其它集群。
