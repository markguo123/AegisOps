# AegisOps 脚本隔离执行与平台服务演进留档

**状态：设计留档，暂缓实现。** 2026-11-18 记录两项后续方向。通用脚本隔离与平台服务演进均暂缓，按各自需求单独启动。

## 一、通用脚本与 Sandbox

### 目标与产品范围

提供通用 Shell 脚本执行能力。用户可通过自定义 Skill 指导 Agent 运行已登记的脚本，用于巡检、数据处理、运维验证等多种任务。AegisOps 提供脚本登记、授权、审批、隔离运行和结果展示。具体任务逻辑由脚本定义，所需文件、网络和凭据按任务授权。

业务发布是一个使用示例。脚本可以从指定 GitLab 仓库拉取代码、构建并推送镜像，再更新 Deployment 并验证发布结果。GitLab 项目地址可由脚本固定。CI/CD 流水线编排和业务节点宿主机执行属于本方案范围之外。

当前 `SKILL.md` 提供流程参考，包内 `scripts/` 是惰性资产。后续新增显式的脚本登记与执行入口，让 Skill 引用受控的脚本 ID 和版本。审阅、审批与执行使用同一份脚本内容摘要，脚本及参数变更后重新审批。

### 与现有 Agent 的分工

保留 Go Agent Runtime 的模型循环、工具调度、审批和聊天输出。新增脚本工具与独立 Runner，只在执行获批脚本时启动一次性 Sandbox。

| 执行入口 | 第一版的执行位置和权限边界 |
| --- | --- |
| 结构化工具、巡检、扫描 | AegisOps 服务端内，继续通过 client-go 和统一请求级授权 |
| Agent 直接调用普通 kubectl | 现有受控子进程，通过本机 Gateway 接入统一授权 |
| `exec_pod` | 在目标业务容器里执行，沿用目标绑定和逐次真人审批 |
| 已登记自定义脚本及其子进程 | 独立 Sandbox，包含脚本调用的 Git、镜像构建器和 kubectl |

普通 kubectl 后续是否迁入独立 Runner 可单独评估。脚本功能的交付只需要扩展工具与执行层。

### 审批、隔离与 Kubernetes 接入

1. 执行前按当前用户权限校验脚本与目标。逐次真人审批绑定脚本版本和摘要、运行参数、目标集群、namespace、操作范围及凭据引用。Runner 启动前复核授权和已批内容，并消费本次执行许可。
2. 每次执行使用独立工作目录和短期执行身份，限制文件挂载、出站网络、运行时间与资源。默认禁止宿主机挂载、容器运行时 socket 和平台服务凭据。脚本所需的外部系统凭据按次注入，脚本包、模型上下文、聊天输出和审计只保留必要的脱敏信息。
3. 脚本若需操作 Kubernetes，由执行器提供指向受控 Gateway 的临时 kubeconfig。沿用[方案 26 的租约和请求级授权契约](./26-方案-工具能力、统一授权与%20Kubernetes%20执行边界设计.md)。独立 Runner 无法直接使用当前的本机回环代理，需提供 Runner 可访问且经过身份认证的入口，由服务端校验执行租约和每条 API 请求。目标集群原始凭据保留在服务端。现有 Secret 专用通道与 Pod exec 审批要求继续适用。
4. 执行结束、取消或超时后撤销租约，终止 Runner 并清理临时资产。审批中心关联脚本版本和执行记录，审计中心记录操作者、审批结果、目标、执行起止和退出状态。退出码、脱敏输出和执行结果由平台直接展示，即使模型没有生成总结也可查看。

### 后续实施验收

- 使用不同用途的脚本验收相同的登记、审批、隔离执行和结果回显路径。涉及 Kubernetes 的脚本按批准范围逐请求校验。
- 脚本或参数变更、许可重放、跨集群或越权访问均被拒绝。拒绝、取消和超时后无法继续使用本次执行凭据。
- 执行结果可在聊天与审计中关联，模型收尾失败时仍能查到实际执行结果。
- 现有内置工具、普通 kubectl 和 `exec_pod` 继续通过各自的既有入口运行。

## 二、服务拆分、多副本与跨进程执行恢复

当前沿用 Web + 单副本 Backend，Go Agent Runtime、工具、Gateway、审批与审计仍按现有边界运行。重启时将中断的运行和待审批交互标记为已失效。审批留痕、审计查询和聊天中的人工确认可在这一架构下完成。

未来有独立扩容、故障隔离或运行连续性需求时，再统一评估 Web、Agent Runtime、Gateway、工具执行、审批和审计的服务边界。具体拆分粒度以容量、隔离和故障恢复目标为依据，可分阶段实施。Gateway 拆出时沿用方案 26 的目标绑定和请求级授权契约。脚本 Sandbox 可以独立实施。

跨进程延续运行需要解决任务领取与租约、审批决定如何唤醒正确的运行实例、实例失效接管、事件续传、撤权与取消传播。Redis 可用于队列、通知或短期协调，选型时也可比较现有数据库与其他消息设施。无论选用哪种调度机制，审批决定、可恢复执行快照、执行账及幂等记录都要有明确的持久事实源。Kubernetes 写请求已发但结果未知时先核对实际状态；恢复前重新校验用户授权、目标、凭据版本和已批参数。

服务拆分、多副本、Redis、跨进程调度和可恢复执行统一留待后续专项评审。当前 P4 的审批与审计范围另行按产品价值评估。
